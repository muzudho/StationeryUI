# 既存画面を少しずつスタイル設定へ移行する

[目次](README.md)

## まず外側の矩形だけを移す

最初からすべてのコントロールを StationeryUiHost へ移す必要はありません。`StationeryLayoutEngine` は描画に依存せず矩形を返すので、既存 UI の配置関数へ結果を渡す方法で始められます。

1. 対象画面の固定座標、余白、部品の親子関係、座標変換を調べます。現在の入力・保存・遷移処理も確認します。
2. ルート viewport と、まず移したい領域だけを models に定義します。対応する C# の役割と Id・型・完全パスを表にして固定します。
3. 画面外周の padding を box-layout へ移し、C# の既存レイアウトに `ContentBounds` を渡します。この段階では部品内部は既存コードのままで構いません。
4. ヘッダー・本文・サイドバーなど、安定した区切りを grid-layout の px / rate へ移します。
5. 必要な画面だけ、work-page-layout のインスペクターや split-pane へ移します。文字サイズ、イベント、データ保存などは C# に残します。
6. 検証・リロード・配布ファイルのコピーを接続してから、移行済みの古い座標計算を取り除きます。

たとえばスタイル管理の `/app/legacyArea` という container を1セルに置き、その内容領域を既存処理に渡します。

```csharp
var result = StationeryLayoutEngine.Arrange(settings, viewportWidth, viewportHeight);
var area = result.ContentBounds["/app/legacyArea"];
// LayoutLegacyControls は利用アプリ側の既存処理。文房具 UI の API ではありません。
LayoutLegacyControls(area.X, area.Y, area.Width, area.Height);
```

既存処理がローカル座標なら、内部は `(0, 0)` 起点で計算し、描画・入力時に area.X/Y を一度だけ足します。論理座標を使う場合は [座標変換](integration.md#px-とホストの論理座標)を挟みます。JSON 側と C# 側で同じ padding を二重に引かないようにします。

この段階で legacyArea の内部部品すべてを models に並べる必要はありません。モデルに追加した未配置部品は親領域全体を引き継ぐため、結果をそのまま全コントロールへ適用すると重なります。**どの要素を JSON が配置し、どの要素を既存 C# が配置するか、適用対象を明示**してください。

## 移すものと残すもの

| 項目 | JSON に移す部分 | C# に残す部分 |
| --- | --- | --- |
| 外周・グループの余白 | box-layout の margin / padding / border 幅 | 枠の描画呼び出し、色、背景 |
| 本文・サイドバーの割合 | grid-layout の行列とセル割当 | 独自の最小幅、内容依存の測定、スクロール |
| 作業ページ | work-page-layout と inspectorModel | ヒント文・ホバー更新・タイマーバー |
| スプリットペーン | 向き・初期比率・仕切り幅・最小ペーンサイズ | 部品生成・入力接続・比率の永続保存 |
| テキスト・ボタン・ツリー | 文房具 Id・階層・配置先 | 文言、テーマ、ツリー項目、クリック等の動作 |
| 複数ページ・ダイアログ | 対応できるモデル構造と矩形 | 表示ページの選択、遷移、モーダル入力制御、黒い幕 |

CSS と同じ指定を想像で追加しないでください。未知のプロパティは無視されることがあります。未対応の機能は C# に残して明記します。たとえば gap が欲しければ空きトラックを用意する案は使えますが、内容依存の折り返しまで grid-layout が解決するわけではありません。

## リロードしても作業状態を保つ

コントロールの生成とレイアウトの適用を別の処理にします。設定変更のたびに画面を生成し直すと、入力中の文字、ツリーの開閉、イベント接続を失いやすくなります。

レイアウトだけの変更では同じ Element に矩形を適用します。モデル階層も変えるなら、検証済みの新ノードへ `RebindModel` で接続し直します。兄弟間で同じ Id は禁止ですが、別の枝には同名があり得るので、全画面を単純に `Id` だけで辞書化しないでください。完全パス、またはページ内で一意と検証した役割で対応付けます。

既存ホストにある C# 専用部品を含めて再接続する場合、それらも新しいツリー内に正しい型で用意する必要があります。部分移行では、スタイル専用の配置ツリーから矩形だけ受け取る方式も選べます。その方式では、ホストのモデルツリーを無理に置き換えません。

## エディターから AI へ渡すもの

スタイル設定エディターの出力は設計図として使います。ファイル名を伸ばして別形式へ変換する必要はありません。設計図と一緒に、アプリの画面の役割、必要なコントロールと処理、今回移す範囲を渡します。エディターは現時点で models / bindings の編集を主目的としていないため、AI は既存モデルとの対応を確認して不足を補います。

別リポジトリーでは、このフォルダー全体を参照できるようにするか、固定した StationeryUI チェックアウトへのパスを指定します。リンク先ソースを読めない環境へ引き継ぐ場合は、必要なソースや版情報も渡してください。

そのまま使える依頼文：

```text
文房具 UI のスタイル設定を、このアプリへ段階的に導入してください。
F12 開発者ウィンドウも導入範囲に含め、一式で取り込んでください。

ガイド: <StationeryUI>/docs/dev/style-settings/README.md
一式の手順: <StationeryUI>/docs/dev/style-settings/full-integration.md
使用する StationeryUI のコミットまたはパッケージ: <固定した版>
対象画面・C# ファイル: <パス>
設計図: <画面名>.stationery-style.json
今回移す範囲: <例: 外周余白と本文／サイドバーの幅>
C# に残す範囲: <例: ツリー内容、イベント、独自グラフ、保存処理>

実装前に、モデルの Id・型・完全パスと既存コントロールの対応を確認する。
models / layouts / bindings を分離し、現行パーサーが対応する指定だけを使う。
必要な API が利用版に存在するか確認し、デモ専用の Id 制約はコピーしない。
読み込み設定とスタイル設定を分け、起動時の fallback と validate を用意する。
Update から監視し、入力処理前に現在のビューポートサイズで配置を適用する。
既存コントロールと入力状態を保持し、同じ領域を C# と JSON で二重配置しない。
未対応の指定は C# に残して、理由と残した箇所を記録する。
同じ版の InspectorGame.cs を取り込み、通常の起動処理より先に --stationery-inspector を分岐する。
F12 の押下、ゲームスレッドでの Inspect、Show / Update、終了時の Dispose を接続する。
複数ホストや独自部品も実際の表示状態・座標を収集し、完全パスで統合する。
リサイズ、明暗、拡大率、不正 JSON、監視の無効→有効、配布先からの起動を確認する。
Debug / Release と publish 出力で F12 の起動・更新・コピー・再表示・親終了時の子終了を確認する。
最後に変更ファイル、検証結果、JSON 化できた範囲と残した範囲を説明する。
```

## 移行完了時の確認

- リサイズ時に再配置される。小さい画面・0幅の領域でも壊れない。
- 倍率や原点変更後も、文字・クリック・IME の位置が一致する。
- 正常な設定変更が反映され、編集中の内容が消えない。
- 欠落 Id、型違い、未接続の必須部品、不正 JSON が採用されず、エラーを確認できる。
- autoReload=false で反映が止まり、true に戻すと停止中の変更が反映される。
- 初回読み込み失敗時の fallback がアプリの必須部品を満たす。
- 別のカレントディレクトリから起動しても、意図した設定を読む。
- build / publish に必要な2ファイルが入り、ユーザーの編集を配布更新で意図せず上書きしない。
- F12 の子プロセスホスト・起動分岐・更新・終了処理が接続され、[一式の完了チェック](full-integration.md#6-一式を取り込めたか確認する)を満たす。

コードを簡潔にするために JSON にない機能を実装済み扱いにしないこと、変更した設定が実際のコントロールへ届くことを確認するのが移行の基準です。
